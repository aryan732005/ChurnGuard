About ChurnGuard

Customer churn prediction for telecom retention

ChurnGuard — self-hosted software for predicting cancellation risk and prioritizing retention outreach.

What this is

ChurnGuard is deployable churn analytics: data audit, feature engineering, calibrated classification, FastAPI inference, experiment tracking, and a retention-focused UI. Run it on your servers with Docker or uvicorn; swap in your CRM export when ready. The bundled demo uses the public IBM Telco benchmark — not your live customer data unless you connect it.

Dataset & provenance

The underlying data is the IBM Telco Customer Churn public benchmark (7,043 anonymised customer records, 21 attributes). If data/telco_churn.csv is missing, the training pipeline generates a synthetic dataset with the same schema — clearly labelled in stats.json. This is not live production CRM data.

Model pipeline (high level)

  1. Load Telco CSV → leakage audit → feature engineering (RFM, interactions)
  2. 80/20 stratified train/test split (no event timestamps — not temporal)
  3. Train candidates with class_weight='balanced' (not SMOTE)
  4. 5-fold stratified CV on train; report mean ± std; multi-seed variance check
  5. Isotonic calibration → cost-based threshold (FP=$15, FN=$1680 LTV)
  6. Export model artifacts + MLflow run + drift reference profile
  7. Serve via FastAPI with SHAP-style linear attributions for explainability

Problem

Telecom providers face ~30% annual churn. Reactive cancellation handling loses revenue and increases acquisition cost. The business need: identify at-risk customers early enough to run targeted retention — without spamming the entire base.

Data & constraints

7,043 anonymised customer records, 21 attributes (tenure, contract, services, billing). Class imbalance: ~70% retained / ~30% churned.

No event timestamp — cross-sectional snapshot only. Point-in-time feature correctness cannot be fully verified without cancellation dates.

Approach

  • Churn definition: Cancellation/non-renewal within ~30 days of snapshot (Telco benchmark convention)
  • Leakage audit on all features — see docs/leakage_audit.md
  • Engineered RFM/trend/interaction features — see docs/feature_engineering.md
  • Label + one-hot encoding; standard scaling for numerics
  • 80/20 stratified hold-out — no time column, so stratified split preserves churn rate
  • 5-fold stratified CV + multi-seed variance — metrics reported as mean ± std
  • Class-weighting (class_weight='balanced') — not SMOTE
  • Probability calibration (isotonic/Platt) before ROI-linked threshold optimisation
  • Drift monitoring — PSI/KS vs training profile on batch uploads; would trigger retrain in production
  • SHAP / coefficient explanations with explicit non-causal disclaimer
Validation strategy

Stratified k-fold cross-validation with held-out test set — chosen because the dataset lacks a reliable event date for temporal splitting.

Trade-offs

Interpretability vs accuracy: Logistic Regression (tuned) was selected — slightly competitive with tree ensembles but easier to explain to stakeholders via coefficients. Recall vs precision: Retention teams often prefer higher recall (catch more churners) at the cost of false alarms; threshold tuning on /insights adjusts this. Class weighting vs SMOTE: Weighting is simpler to defend academically and never alters test data.

Results

Best model: Logistic Regression (Tuned) — ~78.5% ROC AUC on held-out test data vs ~70% naive baseline accuracy. Per-class recall on churners matters more than headline accuracy for campaign design. Error analysis on /insights shows representative false positives and false negatives.

Limitations

  • Cross-sectional data — cannot model seasonality or enforce per-customer temporal cutoffs
  • Synthetic/demo data generation may not reflect live CRM quality
  • Calibration and threshold costs use default assumptions ($15 offer, $1680 LTV)
  • Drift detection is basic PSI/KS — not a full production monitoring stack
  • SHAP attributions are correlational, not causal — recommended actions are heuristics
  • Fairness audit is illustrative, not exhaustive
  • Retrain flow is a simulation — not a production MLOps pipeline

Future work

  • Time-based validation when event timestamps become available
  • Champion/challenger deployment with drift monitoring
  • Causal uplift modeling for retention offer targeting
  • Integration with CRM for automated outreach workflows

Data privacy & production use

Customer identifiers are anonymised in this demo dataset. In production, PII would be tokenised at ingestion, models trained on aggregated features only, and access restricted via role-based auth (Clerk). Predictions would be logged with retention policies — no raw billing data stored in application logs. GDPR-style deletion requests would cascade through the feature store and prediction audit trail.
